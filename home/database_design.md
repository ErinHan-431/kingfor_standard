---
title: 資料庫設計準則
---
> 本處若沒有特別指定資料庫類型時，以 SQL Server 為主。

## 資料庫命名

* 資料庫名稱以系統名稱命名，如有同名資料庫時，則增加組織名稱。
* 資料表名稱應以可辨識之名詞命名，且名詞字彙應具複數性質，可用多字詞之組合命名，然應考慮長度不應太長，以不超過30字元為原則。
* 除因特殊情況經專案經理同意外，不得使用非英文字元 (如中文字)。
* 除資料表外，資料庫物件應使用下列前綴字
* 資料庫物件命名方式如下：
  * 檢視表以其檢視之資料集性質命名。
  * 預存程序、使用者函數與觸發程序以動作命名

## 資料表欄位設計

* 資料表結構至少需滿足第三正規化，刻意進行非正規劃的欄位設計則不在此限
* 資料表之欄位，應依實際儲存之資料性質命名；資料庫物件之參數亦以實際表示之資料性質命名。
* 資料表型態，字串欄位除非規格已規範為固定長度字元可使用char/nchar外，一律使用varchar/nvarchar，如無法確定資料內容是否有含非英文字母時，一律使用Unicode型態 (nchar/nvarchar)。
* 資料表如需儲存大型資料，二進位一律使用varbinary(max)，字串一律使用nvarchar(max)。
* 資料表如需儲存浮點數時，若涉及金錢時，應以decimal儲存，對精度要求不高之數值方可使用float。
* 資料識別碼，以GUID格式為原則，但GUID不可設定為叢集索引，若表格內是以GUID作為主鍵時，應另設立一整數欄位，使用該欄位作為主鍵，並設定自動編號 (Auto-increment)，識別碼欄位則設定唯一性規則。
* 開關性質欄位，以bit為型別。
* 旗標值、列舉值或固定多值欄位，以tinyint或smallint為型別，並對應至程式內相應之列舉值或常數值。
* 日期時間如涉及稽核類型 (如建立日期、最後修改日期) 時，應以由資料庫自動產生為原則。
* 小型二進位資料 (binary) 可使用二進位格式 (varbinary) 或是字串格式，但字串應先編碼為base64格式字串；如為固定長度之二進位資料，宜以固定長度之二進位格式儲存之。
* 資料表間設有鍵值關聯者，除非必要，否則應避免使用串聯刪除 (Cascade Deletion)，防止資料無端被刪除，並且應遵循關聯設定。
* 對於主要查詢或排序用，且非主鍵值(Primary Key)的欄位應設定索引，以提升資料庫查詢之效率降低負荷

## 資料存取設計

* 嚴格禁止使用字串連結方式組建SQL指令，但特殊情況，經軟體開發團隊主管同意者，不在此限，然應加上註解說明其特殊情況為何。
* SQL指令參數以參數物件 (Parameter Object) 給予為原則，嚴格禁止使用字串連結方式設定參數值。
* 資料存取作業以最小權限為原則 (僅授予資料之讀寫權限，無異動資料庫結構與物件之權限)。
* 資料查詢分頁以OFFSET指令為主，除系統資料庫版本為SQL Server 2012 (含) 之前，可允許RANK實作分頁查詢外。
* 如資料表中存有大型數值欄位時，查詢資料集之指令不應包含該欄位，以避免查詢效能受影響。
* 查詢指令宜參照可搜尋式參數 (Searchable Argument; SARG) 原則設計查詢條件，以加快搜尋速度。
* 跨資料表之資料異動，或批次資料異動時，應設定交易 (Transaction)，以確保異動之一致性。
* 使用ORM技術存取資料庫時，應注意：
  * 避免一次取出大量資料。
  * 避免查詢指令產生1+n查詢效應。
  * 複雜查詢宜注意相關指令之使用，避免隱藏1+n查詢。
  * 適當使用ORM指令以組合出適當之SQL指令。
  * 查詢時應關閉變更追踪 (Change Tracking) 功能。
  * 適當實作分頁。
